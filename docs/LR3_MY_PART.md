# ЛР3: распределение ответственности команды

Чтобы каждый пункт имел ровно одного ответственного, задачи закреплены так.

## Моя часть

- **№1** — единый сценарий первоначальной настройки (`make setup`).
- **№2** — точные версии runtime- и developer-зависимостей (`requirements.txt`, `requirements-dev.txt`, `.python-version`).
- **№3** — единый интерфейс Makefile для setup/run/test/quality/migrate/backup/restore/verify/up/down/container-check.
- **№4** — unit-тесты и API/DB-интеграционные тесты.
- **№5** — ошибки, boundary cases и бизнес-правила; в частности ограничение грузоподъёмности катера.
- **№7** — Ruff formatter/lint, Bandit SAST, JUnit- и coverage-отчёты.
- **№13** — обязательная последовательная команда `make verify`.
- **№14** — правила, запрещающие пропуск тестов и необоснованное ослабление проверок.

## Часть сокомандника

- **№6** — отдельная тестовая конфигурация и изоляция данных.
- **№8** — миграционный инструмент и не менее трёх миграций.
- **№9** — проверка миграций на чистой и уже заполненной БД.
- **№10** — новая функция, изменяющая схему.
- **№11** — создание backup и реализация restore.
- **№12** — демонстрация восстановления после изменения/удаления данных.
- **№15** — проведение своей новой функции через полный `make verify`.

## Интерфейсы между частями

- `make migrate` автоматически использует `alembic upgrade head`, когда в проекте появляется `alembic.ini`; до этого используется SQL baseline проекта.
- `make backup` создаёт `backup.sql`; `make restore` читает файл, заданный через `BACKUP_FILE` (по умолчанию `backup.sql`). Реальное восстановление и эксперимент с повреждением данных — ответственность исполнителя пункта №11/12.
- Локальные тесты используют временную SQLite БД, если `TEST_DATABASE_URL` не задан. CI запускает этот же API-набор на PostgreSQL в отдельной БД `fishing_test`.
- Тестовая конфигурация PostgreSQL обязана указывать на базу с суффиксом `_test`/`_tests`; fixture откажется сбрасывать схему БД с другим именем.
- Изменения интегрируются в общий репозиторий через feature-ветку, PR, `make verify`, review и merge. Прямой push в `main` не используется.

## Найденное исправление по действующему ТЗ

Тесты выявили, что endpoint `GET /api/reports/catch-by-period` должен возвращать количество рейсов, общий вес и общее число банок. Реализация и веб-интерфейс приведены в соответствие с формулировкой FR-09; регрессионные тесты проверяют фильтрацию периода и нулевой результат для пустой БД.
