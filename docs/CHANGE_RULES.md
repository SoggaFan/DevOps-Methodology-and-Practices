# Правила внесения и приемки изменений

## 1. Порядок работы

1. Любое изменение начинается с задачи с кратким описанием и критериями приемки.
2. Для задачи создаётся отдельная ветка от актуального `main`: `feature/<short-name>`, `fix/<short-name>` или `chore/<short-name>`.
3. Изменение выполняется небольшими логическими коммитами. Сообщения коммитов описывают результат изменения и не содержат секретов.
4. Перед публикацией ветки обязательно выполнить `make verify`.
5. В удалённом репозитории создаётся Pull Request / Merge Request в `main`.
6. В PR/MR прикладываются описание, ссылка на задачу и результаты проверок. Для существенных изменений показывается API/БД сценарий.
7. После ревью и успешных проверок выполняется merge. Прямая запись в `main` для учебного процесса запрещена.
8. После принятия изменений версия фиксируется Git-тегом. Для первой завершённой версии используется `v0.1.0`.

## 2. Обязательные проверки

Перед PR/MR:

```bash
make quality
make test
make verify
```

Для проверки контейнерного запуска:

```bash
make up
make container-check
make down
```

Проверка отсутствия случайно добавленного `.env`:

```bash
git ls-files .env
```

Команда не должна выводить путь `.env`.

## 3. Запрещённые действия

- Нельзя коммитить `.env`, пароли, токены, ключи и другие секреты.
- Нельзя коммитить `.venv/`, `__pycache__/`, `.pytest_cache/`, `postgres_data/`, IDE-файлы и локальные backup-файлы.
- Нельзя выполнять `git push --force` в `main`.
- Нельзя изменять историю уже опубликованных коммитов в `main`.
- Нельзя сливать PR/MR с красными обязательными проверками.
- Нельзя принимать изменение без проверки критериев задачи.

## 4. Правила приемки

Изменение принимается, если:

- задача понятна и критерии приемки выполнены;
- `make verify` проходит;
- нет секретов и запрещённых файлов в Git;
- изменения просмотрены ревьюером;
- конфликт с `main`, если он возник, разрешён явно и проверен повторно;
- описание PR/MR соответствует фактическому diff.

## 5. Версионирование

Тег ставится после принятого merge в `main`:

```bash
git tag -a v0.1.0 -m "ЛР1: первая минимально рабочая версия"
git push origin v0.1.0
```
