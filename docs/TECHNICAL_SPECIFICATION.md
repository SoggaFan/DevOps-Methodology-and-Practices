## 2. Назначение и цели создания продукта

### 2.1. Назначение

Система предназначена для учета катеров рыболовной фирмы, команд, выходов катеров в рейсы, сортов рыбы и фактического улова.

Система предоставляет HTTP API для выполнения операций с указанными данными и формирует агрегированный отчет по улову.

### 2.2. Цели

1. Централизовать хранение основных данных о рыболовной деятельности.
2. Исключить несогласованные записи за счет внешних ключей и валидации.
3. Контролировать соблюдение ограничения грузоподъемности катера.
4. Предоставить простой HTTP API для проверки функциональности.
5. Обеспечить воспроизводимый запуск приложения и БД.
6. Продемонстрировать сквозной Git-процесс разработки изменения.

## 3. Характеристика объекта автоматизации

### 3.1. Описание объекта автоматизации

Объект автоматизации — учет деятельности рыболовной фирмы. В минимальной версии автоматизируются следующие сущности:

| Сущность | Назначение | Ключевые поля | Связи |
|---|---|---|---|
| Катер | Учет плавсредств | id, name, registration_no, capacity_kg | 1:N с рейсами |
| Команда | Учет экипажей | id, name, captain | 1:N с рейсами |
| Сорт рыбы | Справочник видов продукции | id, name, latin_name | 1:N с уловом |
| Рейс | Учет выхода катера на промысел | id, boat_id, crew_id, даты | N:1 с катером и командой; 1:N с уловом |
| Улов | Учет фактического улова | id, trip_id, fish_type_id, cans, weight_kg | N:1 с рейсом и сортом рыбы |

### 3.2. Участники процесса

В предметной области выделяются:

- **диспетчер/менеджер** — ведет справочники и регистрирует рейсы и улов;
- **капитан команды** — источник данных о проведенном рейсе и улове;
- **администратор/разработчик** — отвечает за запуск системы и сопровождение.

Аутентификация пользователей является обязательной частью базового функционала системы. Разграничение прав по ролям в ЛР1 не реализуется.

## 4. Требования к продукту

### 4.1. Общие требования

**АРХ-01.** Продукт должен состоять из HTTP API и реляционной БД.
**АРХ-02.** Приложение должно запускаться локально через Docker Compose одной командой `make up`.
**АРХ-03.** Приложение должно быть доступно на `http://localhost:8000`.
**АРХ-04.** Доступ к PostgreSQL из контейнера API должен осуществляться по внутреннему имени сервиса `db`.

### 4.2. Функциональные требования

**FR-01. Проверка работоспособности.**
`GET /health` должен возвращать HTTP 200 и статус `ok`, одновременно проверяя соединение API с БД.

**FR-02. Учет катеров.**
Система должна предоставлять просмотр и добавление катеров. Для катера обязательны название, регистрационный номер и грузоподъемность в килограммах. Регистрационный номер должен быть уникальным.

**FR-03. Учет команд.**
Система должна предоставлять просмотр и добавление команд. Для команды обязательны название и ФИО капитана.

**FR-04. Учет сортов рыбы.**
Система должна предоставлять просмотр и добавление сортов рыбы. Название сорта должно быть уникальным.

**FR-05. Учет рейсов.**
Система должна предоставлять просмотр и создание рейсов. Рейс обязан ссылаться на существующий катер и существующую команду. Дата возвращения не может быть раньше даты выхода.

**FR-06. Учет улова.**
Система должна предоставлять просмотр и добавление записей улова. Каждая запись обязана ссылаться на существующий рейс и сорт рыбы и содержать положительное число банок и положительную массу.

**FR-07. Контроль грузоподъемности.**
При добавлении улова система должна суммировать уже зарегистрированный улов рейса и отклонять новую запись, если итоговый вес превышает грузоподъемность катера, связанного с рейсом. Ошибка должна возвращаться как HTTP 422.

**FR-08. Отчетность.**
Система должна формировать агрегированный отчет `GET /api/reports/catch-by-trip` с общей массой улова по каждому рейсу.

**FR-09. Отчет по периоду.**
Система должна поддерживать `GET /api/reports/catch-by-period?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD`, возвращающий итоговые показатели за период: количество рейсов, общую массу улова и общее количество банок.

### 4.3. Требования к обработке ошибок

**ERR-01.** Некорректные входные данные должны отклоняться с HTTP 422.
**ERR-02.** Ссылка на отсутствующую сущность должна приводить к HTTP 404.
**ERR-03.** Дубликат уникального значения должен приводить к HTTP 409.
**ERR-04.** При отказе БД API не должен сообщать об успешной проверке `/health`.
**ERR-05.** При отсутствии действующей аутентификации доступ к защищенным `/api/*` endpoints должен отклоняться с HTTP 401.

### 4.4. Требования к данным

**DATA-01.** PostgreSQL используется как реляционная БД.
**DATA-02.** Для связей между сущностями должны использоваться внешние ключи.
**DATA-03.** Для идентификаторов используются первичные ключи.
**DATA-04.** Поля `capacity_kg`, `cans` и `weight_kg` должны иметь положительные значения.
**DATA-05.** Для `trips.return_date` действует ограничение `return_date >= departure_date`.
**DATA-06.** Удаление рейса должно удалять связанный улов, чтобы не оставлять некорректные зависимые записи.

### 4.5. Требования к конфигурации

**CONF-01.** Параметры подключения к БД задаются переменными окружения.
**CONF-02.** В репозитории хранится `.env.example` без реальных секретов.
**CONF-03.** Файл `.env` не должен отслеживаться Git.
**CONF-04.** Учетные данные администратора должны задаваться переменными окружения.

### 4.6. Требования к надежности и сопровождаемости

**REL-01.** PostgreSQL должен иметь health-check.
**REL-02.** API должен иметь health-check `/health`.
**REL-03.** Запуск и остановка среды должны быть стандартизованы командами Makefile.
**REL-04.** Локальные проверки должны запускаться одной командой `make verify`.
**REL-05.** Исходники должны быть разделены на код приложения, SQL, тесты и документацию.

### 4.7. Требования к безопасности

**SEC-01.** Секреты БД не должны храниться в исходном коде.
**SEC-02.** `.env`, кэши, виртуальное окружение и локальные файлы IDE должны быть исключены из Git.
**SEC-03.** Пароли пользователей не должны храниться в БД в открытом виде; приложение сохраняет только стойко хешированное значение.
**SEC-04.** Для доступа к бизнес-операциям используется HTTP Basic с логином и паролем.
**SEC-05.** Пароль администратора задается через переменную окружения и не должен храниться в исходном коде или Git-репозитории.

## 4.11. Аутентификация и авторизация доступа

Для ЛР1 реализуется базовая аутентификация без ролевого разграничения прав.

- Пользователь хранится в таблице `users` с уникальным именем и хешем пароля.
- Администратор создается при старте приложения из переменных `ADMIN_USERNAME` и `ADMIN_PASSWORD`, если такой пользователь отсутствует.
- `POST /auth/login` проверяет логин и пароль через HTTP Basic и возвращает текущего пользователя.
- `GET /auth/me` возвращает текущего пользователя и требует корректные HTTP Basic credentials.
- Все `/api/*` endpoints требуют корректные учетные данные HTTP Basic.
- `/health`, `/docs` и `/openapi.json` остаются доступными без аутентификации для служебной проверки и документации.

## 6. Порядок контроля и приемки системы

### 6.1. Предварительные проверки

Исполнитель должен выполнить:

```bash
make verify
```

Команда должна завершиться без ошибок.

### 6.2. Проверка контейнерного окружения

```bash
make up
make container-check
```

Ожидается:

- контейнер PostgreSQL находится в состоянии `healthy`;
- контейнер API находится в состоянии `Up`;
- `GET /health` возвращает HTTP 200.

### 6.3. Проверка функциональности

Проверяются следующие сценарии:

1. получение списка катеров;
2. создание катера;
3. создание команды;
4. создание сорта рыбы;
5. создание рейса с корректными внешними ключами;
6. создание записи улова;
7. отклонение улова при превышении грузоподъемности;
8. получение агрегированного отчета;
9. получение отчета за период;
10. проверка ошибок 404, 409 и 422;
11. вход с корректными учетными данными;
12. отказ во входе с неверным паролем;
13. отказ в доступе к `/api/*` без логина и пароля;
14. успешный вызов защищенного endpoint с корректными учетными данными HTTP Basic.

### 6.4. Проверка данных

Через `psql` проверяется наличие пяти основных таблиц и корректность внешних ключей:

```bash
docker compose exec db psql -U fishing -d fishing
```

Внутри БД:

```sql
\dt
SELECT * FROM boats;
SELECT * FROM crews;
SELECT * FROM fish_types;
SELECT * FROM trips;
SELECT * FROM catches;
```

### 6.5. Проверка Git-процесса

Проверяется наличие:

- отдельной feature-ветки;
- нескольких осмысленных коммитов;
- Pull Request / Merge Request;
- merge в `main`;
- тега `v0.1.0`;
- демонстрации конфликта и его разрешения.

### 6.6. Критерии приемки

Работа считается принятой, если все обязательные пункты ЛР1 и настоящего ТЗ выполнены и подтверждены живой демонстрацией.
